Hexapod wall-climbing robot · troubleshooting case file · 2026-09-02 to 09-06

The ground loop at the instant of relay closure

The Raspberry Pi 5 would randomly lose power and die at the instant the servo relay closed. Over three days the suspicion moved from "valve coils" to "5 V margin" to "18 servos drawing a big current", and was finally settled by a log line 14 milliseconds long and one USB cable. This case file records the detours, the tools that actually worked, and the lessons worth carrying to the next project. Sequel 09-06: with the USB isolator fitted it still died at closure, and one island test narrowed the entry to the buck module itself; the conclusion changed from "one path" to "two entries".

Machine: Pi 5 + Servo2040 + 18 servos + six valves Power: 2S LiPo → 5 V buck for the Pi; relay switches the servo positive Symptom: status LED green → solid red, SSH drops, needs a power cycle
Root cause
The closure pulse has two entries: the USB ground loop (settled 09-04, cut by the isolator); and a buck module with under 1 V of margin on the 2S pack, pulled down by the pulse (09-06)
Decisive evidence
USB unplugged, ten closures 0x0; plugged back in, first closure 0x50000; with the isolator fitted it still died tens of ms after closure; with the buck IN− removed, Pi ground and battery negative are open
Remedies
USB isolator (fitted); replace the buck with a low-dropout synchronous buck or buck-boost suited to 2S; pre-charge demoted to secondary
01

Symptoms and constraints

The startup script first energizes the six solenoid valve coils one by one into the exhaust position, then closes the servo relay. With some probability the Raspberry Pi dies right in this window: solid red LED, green LED off, SSH unreachable, only a power cycle helps. On the Pi 5 this LED state is the halted state after the PMIC has cut power to the processor, the same as after sudo halt.

No oscilloscope at hand. The only tools were a multimeter, the Pi's own PMIC readout (vcgencmd pmic_read_adc, which in practice runs at 10 Hz) and the kernel log. The death is a power cut; at the instant of death no process can write to disk any more, so everything must "leave a trace before dying".

02

Tools built for this

Black box

Before every high-current step (each valve coil energized, relay closure, firmware enable) write one line and fsync; whichever line the log stops at, the culprit is the next step. A background thread records the Pi's 5 V input voltage and undervoltage flag every 0.1 s, each line flushed to disk. After closure, the servo bus voltage and current are sampled again at 0.05 / 0.15 / 0.30 s. The four startup scripts share the same convention, with logs in software/logs/<tag>_time.log.

Forensics script

scripts/pi_forensics.sh setup switches the kernel log to persistent storage synced every second; it must be run once before a crash. After the power cycle, check brings out in one go: the kernel tail of the previous boot, the real boot time (the Pi 5 has no RTC battery, so the time in the boot list is a fake clock saved at the last shutdown), the current undervoltage flags and PMIC voltages, the firmware power node, and the tail of the latest black box.

05

A/B experiment

Same boot, same program, touching only GPIO17: close, read the flag after 0.2 s, wait 2 s, open, wait 2 s, repeat ten times. No serial port opened, no valves touched; the servos are energized but produce no torque without PWM. The only variable is the USB cable between the Pi and the Servo2040.

USB cable unplugged

10 / 10 → 0x0

Ten closures, the sticky bit never set.

USB cable plugged back in

1st time → 0x50000

Set on the very first closure, and stays set for the next nine.

There is no second explanation: the pulse's path into the Pi is the ground of this USB cable.

import subprocess, time, lgpio
h = lgpio.gpiochip_open(4)          # Pi 5 main gpiochip (0 on newer kernels)
lgpio.gpio_claim_output(h, 17, 0)   # GPIO17 = relay IN1
def thr(): return subprocess.run(["vcgencmd","get_throttled"], capture_output=True, text=True).stdout.strip()
print("before closure", thr())
for i in range(10):
    lgpio.gpio_write(h, 17, 1); time.sleep(0.2); print(f"after closure {i+1}: {thr()}", flush=True)
    time.sleep(2); lgpio.gpio_write(h, 17, 0); time.sleep(2)
06

The path the pulse takes

The buck module's green LED is corroborating evidence

The new module is an XL4015 5 A constant-current/constant-voltage board; the silkscreen on the back says red = constant current, blue = charging, green = full. The sense resistor R10 is 50 mΩ, in series between OUT− and IN−, i.e. between the Pi's ground and the battery negative; the output voltage is regulated against IN−, so any current through it is subtracted directly from the 5 V the Pi sees. The blue LED flashing green at closure means the current comparator saw the output current drop to near zero or even reverse, which can only be an external pulse passing through it. The old fixed 5 V module had no such resistor and the crash happened anyway, so it is not the root cause, just an amplifier of the dip.

Sequel: after the isolator (09-06)

The USB isolator was the cleanest of the three remedies, and once fitted it completed the third leg of the A/B: cable plugged in, an ADuM3160 in the middle, ten closures alone all 0x0. But on the same day the Pi died twice around it, the second time with a black box running. This section records the way from "path broken" to "more than one entry" to "the remaining entry is the buck module itself".

  • 09-06power_reset control: still reads 2 after several normal poweroffs / reboots.On this machine the field cannot tell a PMIC cut from a normal shutdown; withdrawn as evidence (sections 02, 07). The LED color is what tells the kind of death: solid red is a PMIC cut.

Closure alone is clean, the real scripts die: the difference is before closure

Closure only (GPIO17 script)

10 / 10 → 0x0

Valves not energized, serial port closed. The battery carries only the quiescent current of the Pi and the Servo2040.

Real scripts (body_lean / walk_teleop)

dies at closure

Six valves already energized, about 25 W, roughly 3.5 A more on the battery side; serial port open. Serial data cannot carry a pulse across the isolator, so the valve load is the only item left.

The valve load creates no new ground path. It does one thing only: it pulls the battery voltage down a notch beforehand. So the only entry left is the Pi's one remaining wire, the buck module itself.

The buck module's margin

ItemValueSource

Under 1 V of margin, and one pulse eats it all. The XL4015 is an old non-synchronous 180 kHz part with a slow loop; it cannot fill a sub-millisecond hole in its input, so the output sags for a fraction of a millisecond and the PMIC cuts power. This also accounts for the green LED in section 06: when the output current momentarily drops to zero, the CC/CV board reads it as "full". Section 06 attributed the flash to the pulse crossing the sense resistor; the module losing regulation flashes it just the same, so the LED no longer separates the two. The old fixed 5 V module put out only 4.89 V unloaded, the same high-dropout kind of part starved on a 2S pack, the same disease.

The explanation leaves one gap: the first death after the isolator was fitted happened in the GPIO17 script, with the valves off. It says the system was already at the edge, where the battery's state at the time or one slightly worse contact bounce is enough to push it over; and it says "ten clean closures" is not a proof of safety, only ten closures that did not catch it.

09

Conclusion and remedies

The pulse that charges the servo-side capacitance at closure has two entries into the Pi. The first is the USB ground loop settled on 09-04: the pulse floods in through the USB ground between the Pi and the Servo2040, and the drop across the GND Dupont wire and the sense resistor is judged by the PMIC as undervoltage. That path is real, the sticky bit proved it, and the isolator has cut it. The second is the buck module itself, narrowed down on 09-06: the XL4015 needs at least 6.7 V in for 5.19 V out, the 2S pack has only 1 V of margin left under the valve load, the closure pulse pulls the battery down, the buck loses regulation, the output sags, the PMIC cuts. The first entry had been masking the second.

  1. Replace the buck module. Ignore the broad "input range" figure and look at the dropout: it must hold 5.1 V with the input down to a little over 6 V. Synchronous rectification, 5 A or more, dropout under 0.5 V; or go straight to a buck-boost, untroubled anywhere from 5 to 8.4 V. Old non-synchronous parts like the XL4015 and LM2596 were the wrong choice for a 2S pack from the start.
  2. Keep the USB isolator. The path it cut is real; remove it and the sticky bit comes back.
  3. Pre-charge of the servo rail demoted to secondary. With a suitable buck it is no longer necessary; it can still be fitted, but it only softens the pulse and does nothing for the margin.

A large capacitor plus a Schottky diode at the buck input buys only a few milliseconds and costs an extra diode drop; not recommended. A capacitor across the Pi's 5 V pins likewise only treats the symptom. Whether R050 is bridged no longer matters.

Verification: after the swap, run the real scripts (the ones that energize the valves) several times; the criterion is no sticky bit and no death. Two supporting experiments are optional: measure the battery with a multimeter after the valves are energized, below 7.5 V means out of spec; run walk_teleop --vent off three times, and if that stays clean while body_lean dies, the valve load is the trigger.

The software side is already in place: two-step closure, a black box with the same convention in the four startup scripts, the real timeline in the forensics script. --startup-gap is no longer needed.

10

Lessons to take away

A power-cut death can only leave traces before dying

Write one line and fsync before every high-current step; whichever line the log stops at, the culprit is the next step. Without that line, three days of investigation would not have moved one step.

Find a deterministic stand-in for a sporadic fatal event

The sticky bit is set on every closure; no need to wait for a crash. The experimental criterion changed from "dies or not" to "sets or not"; one reboot gives an answer, and "did not die" is no longer non-information.

Point sampling cannot see transients

In the same tick the ADC read 5.105 V, the fast comparator had already latched undervoltage. A multimeter and 10 Hz sampling are blind to a hundred-microsecond event; do not let their "normal" reading rule out a fault.

Big current is not the problem; the switching instant is

A sustained 6.67 A surge left the Pi unmoved; closure at 0 A caused undervoltage every time. What matters is di/dt and which path the current takes, not the amperes.

Ground is not a point

The USB cable, the sense resistor and the Dupont wire are each a resistance in the ground return. When two boards share ground and each returns to the battery separately, the pulse will pick a path you did not think of.

Change one variable at a time, within one boot

Unplug one cable, close ten times, plug back in, close again; the contrast between 0x0 and 0x50000 leaves no room for interpretation. Faster than swapping modules, and cheaper too.

The manufacturer's one sentence needs a control too

power_reset=2 is backed by a verbatim forum sentence and was read after both crashes, so at the time it passed as the PMIC's own testimony. Read again on 09-06 after a normal shutdown: still 2. A reading without a control group is not evidence.

Measure the evidence before swapping parts

Swapping the buck module only proved "static voltage is not the root cause"; that conclusion is worth something, but had the sticky bit been checked first, that step could have been skipped.

One path proven is not the only path

The A/B nailed the USB ground loop beyond dispute, but it only proved that this path exists, not that no other does. Fix it and the crash comes back in a rarer form.

Island test: disconnect the wire you know about, then measure

The Pi's ground is supposed to be connected to the battery negative, so continuity proves nothing. Pull the wire the design put there and measure again; open means an island, and the remaining entry can only be on that wire itself.
