Hexapod wall-climbing robot · troubleshooting case file · 2026-09-02 to 09-04

The ground loop at the instant of relay closure

The Raspberry Pi 5 would randomly lose power and die at the instant the servo relay closed. Over three days the suspicion moved from "valve coils" to "5 V margin" to "18 servos drawing a big current", and was finally settled by a log line 14 milliseconds long and one USB cable. This case file records the detours, the tools that actually worked, and the lessons worth carrying to the next project.

Machine: Pi 5 + Servo2040 + 18 servos + six valves Power: 2S LiPo → 5 V buck for the Pi; relay switches the servo positive Symptom: status LED green → solid red, SSH drops, needs a power cycle
Root cause
The charging pulse at relay closure floods into the Pi through the USB ground, and the PMIC calls it undervoltage and cuts power
Decisive evidence
Same boot, only one USB cable changed: unplugged, ten closures all 0x0; plugged back in, the first closure gives 0x50000
Remedies
USB isolator; pre-charge soft start of the servo rail; star grounding
01

Symptoms and constraints

The startup script first energizes the six solenoid valve coils one by one into the exhaust position, then closes the servo relay. With some probability the Raspberry Pi dies right in this window: solid red LED, green LED off, SSH unreachable, only a power cycle helps. On the Pi 5 this LED state is the halted state after the PMIC has cut power to the processor, the same as after sudo halt.

No oscilloscope at hand. The only tools were a multimeter, the Pi's own PMIC readout (vcgencmd pmic_read_adc, which in practice runs at 10 Hz) and the kernel log. The death is a power cut; at the instant of death no process can write to disk any more, so everything must "leave a trace before dying".

02

Tools built for this

Black box

Before every high-current step (each valve coil energized, relay closure, firmware enable) write one line and fsync; whichever line the log stops at, the culprit is the next step. A background thread records the Pi's 5 V input voltage and undervoltage flag every 0.1 s, each line flushed to disk. After closure, the servo bus voltage and current are sampled again at 0.05 / 0.15 / 0.30 s. The four startup scripts share the same convention, with logs in software/logs/<tag>_time.log.

Forensics script

scripts/pi_forensics.sh setup switches the kernel log to persistent storage synced every second; it must be run once before a crash. After the power cycle, check brings out in one go: the kernel tail of the previous boot, the real boot time (the Pi 5 has no RTC battery, so the time in the boot list is a fake clock saved at the last shutdown), the current undervoltage flags and PMIC voltages, the firmware power node, and the tail of the latest black box.

Reading two read-only interfaces

The ADC minimum over the whole run was 5.072 V; it never once read below the threshold, yet the flag was set. So the dip is far shorter than 100 ms; point sampling cannot touch it, and only the sticky bit latched by the PMIC's internal fast comparator can see it.

05

A/B experiment

Same boot, same program, touching only GPIO17: close, read the flag after 0.2 s, wait 2 s, open, wait 2 s, repeat ten times. No serial port opened, no valves touched; the servos are energized but produce no torque without PWM. The only variable is the USB cable between the Pi and the Servo2040.

USB cable unplugged

10 / 10 → 0x0

Ten closures, the sticky bit never set.

USB cable plugged back in

1st time → 0x50000

Set on the very first closure, and stays set for the next nine.

There is no second explanation: the pulse's path into the Pi is the ground of this USB cable.

import subprocess, time, lgpio
h = lgpio.gpiochip_open(4)          # Pi 5 main gpiochip (0 on newer kernels)
lgpio.gpio_claim_output(h, 17, 0)   # GPIO17 = relay IN1
def thr(): return subprocess.run(["vcgencmd","get_throttled"], capture_output=True, text=True).stdout.strip()
print("before closure", thr())
for i in range(10):
    lgpio.gpio_write(h, 17, 1); time.sleep(0.2); print(f"after closure {i+1}: {thr()}", flush=True)
    time.sleep(2); lgpio.gpio_write(h, 17, 0); time.sleep(2)
06

The path the pulse takes

The buck module's green LED is corroborating evidence

The new module is an XL4015 5 A constant-current/constant-voltage board; the silkscreen on the back says red = constant current, blue = charging, green = full. The sense resistor R10 is 50 mΩ, in series between OUT− and IN−, i.e. between the Pi's ground and the battery negative; the output voltage is regulated against IN−, so any current through it is subtracted directly from the 5 V the Pi sees. The blue LED flashing green at closure means the current comparator saw the output current drop to near zero or even reverse, which can only be an external pulse passing through it. The old fixed 5 V module had no such resistor and the crash happened anyway, so it is not the root cause, just an amplifier of the dip.

08

Conclusion and remedies

The root cause is the pulse that charges the servo-side capacitance at the instant the relay closes; it floods into the Raspberry Pi through the USB ground between the Pi and the Servo2040, and the drop it produces across the GND Dupont wire and the sense resistor is judged by the PMIC as input undervoltage. A shallow dip leaves only a sticky bit; a deep one makes the PMIC cut power, shown as the solid red LED.

  1. USB isolator. A full-speed isolator such as the ADuM3160; 12 Mbps is enough for the Servo2040 serial link. Inserted between the Pi and the Servo2040, it physically breaks the ground loop. The cleanest cut.
  2. Pre-charge soft start of the servo rail. A second small relay in series with a 4.7 Ω 5 W resistor closes first for 100 ms to charge the capacitance, then the main relay closes; or swap in a P-MOS soft-start module. It can be verified first by manually pre-charging through a 10 Ω resistor across the contacts for a second before closing and watching the sticky bit.
  3. Star grounding. The Servo2040 GND and the buck module's IN− each run in short thick wire straight to the same point on the battery negative; no Dupont wire for the Pi's 5V/GND. This only mitigates; it does not break the path.

A capacitor across the Pi's 5 V pins only treats the symptom: at the Pi 5's ~0.7 A, 2200 µF holds a 0.4 V dip for about 1 ms. The XL4015's R050 can be bridged with solder so that OUT− equals IN− directly; the module degrades into a plain regulator and the LEDs stop working, which is fine. Once the path is broken it is harmless by itself and can be left alone.

The software side is already in place: two-step closure, a black box with the same convention in the four startup scripts, real timeline and power_reset interpretation in the forensics script. --startup-gap is no longer needed.

09

Lessons to take away

A power-cut death can only leave traces before dying

Write one line and fsync before every high-current step; whichever line the log stops at, the culprit is the next step. Without that line, three days of investigation would not have moved one step.

Find a deterministic stand-in for a sporadic fatal event

The sticky bit is set on every closure; no need to wait for a crash. The experimental criterion changed from "dies or not" to "sets or not"; one reboot gives an answer, and "did not die" is no longer non-information.

Point sampling cannot see transients

In the same tick the ADC read 5.105 V, the fast comparator had already latched undervoltage. A multimeter and 10 Hz sampling are blind to a hundred-microsecond event; do not let their "normal" reading rule out a fault.

Big current is not the problem; the switching instant is

A sustained 6.67 A surge left the Pi unmoved; closure at 0 A caused undervoltage every time. What matters is di/dt and which path the current takes, not the amperes.

Ground is not a point

The USB cable, the sense resistor and the Dupont wire are each a resistance in the ground return. When two boards share ground and each returns to the battery separately, the pulse will pick a path you did not think of.

Change one variable at a time, within one boot

Unplug one cable, close ten times, plug back in, close again; the contrast between 0x0 and 0x50000 leaves no room for interpretation. Faster than swapping modules, and cheaper too.

Find the manufacturer's one sentence first

The meaning of power_reset=2 is one verbatim sentence on the forum; reading it after both crashes is the PMIC's own testimony. One lookup saves half a day of guessing.

Measure the evidence before swapping parts

Swapping the buck module only proved "static voltage is not the root cause"; that conclusion is worth something, but had the sticky bit been checked first, that step could have been skipped.
